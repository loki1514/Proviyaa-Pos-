PROVIYAA POS — V1 DECISIONS AND QUESTIONS

Purpose
-------
This document records owner-approved V1 decisions. Each decision remains in force unless the owner explicitly replaces it in a future decision record. Unresolved details remain clearly separated below; they must not be silently assumed.

OWNER-APPROVED V1 DECISIONS
----------------------------
D01 — Windows POS and local hardware
- The first POS application target is Windows.
- Each enrolled location uses a local SQLite database on the POS laptop.
- The POS supports USB/LAN printer connectivity.
- The POS works without internet and synchronizes to Supabase/Proviyaa when connectivity is available.
- The initial operating profile is POS with an 80 mm printer.
- A scanner is optional.
- Kitchen output initially uses same-device kitchen printing.
- These choices supersede the earlier open question about Windows versus Android as the first target.

D02 — Offline topology
- One primary POS per location supports offline operation.
- Multi-terminal offline coordination and separate KDS offline coordination are deferred.
- The POS must not imply shared offline consistency across multiple devices in V1.

D03 — Pilot payment posture
- The first pilot is cash-first.
- Digital payments remain pending verification until an approved provider integration exists.
- A local digital-payment action must not be represented as provider-confirmed payment.

D04 — Connectivity and authorization limits
- Offline staff authorization duration: 24 hours.
- Device heartbeat interval: 60 seconds.
- OneCity restaurant reachability timeout: 5 minutes.
- The POS preserves local evidence when authorization or connectivity expires; it does not silently delete unsynced records.

D05 — Synchronization direction
- PowerSync is the selected synchronization direction, subject to a Flutter compatibility and cost spike.
- Do not build a competing custom synchronization system for the same records.
- The spike may validate compatibility, cost, operational limits and failure behavior; it does not authorize production rollout by itself.

D06 — Supabase environment and ownership
- POS work uses a separate Supabase staging environment.
- The existing Proviyaa OS repository owns central schema migrations and shared contracts.
- The POS must not create a competing migration history or apply changes to production under these decisions.

D09 — V1 finance posture
- Apply the V1 finance rules already recorded in the approved POS source/PRD context:
  - Keep order, kitchen, delivery, payment and settlement states separate.
  - Store money as integer minor units with currency and explicit rounding rules.
  - Verify and deduplicate provider confirmations server-side.
  - Permit offline cash evidence; keep digital evidence pending until provider verification.
  - Use immutable financial postings or a validated equivalent; corrections are reversals, not edits to settled history.
  - Keep refunds authorized, idempotent and linked to the original payment.
  - Keep customer payments, Proviyaa subscription fees, merchant payable, platform/rider fees, rider cash custody and settlement distinct.
  - Do not execute settlement payouts without reconciliation and required evidence.
- These decisions do not approve jurisdiction-specific tax, invoice, fee percentage or settlement rules; those remain open below.

D10 — Local database technology and recovery
- Use Drift with SQLite through a Flutter application dependency.
- Create the database automatically on first launch.
- Use explicit numbered local migrations.
- Do not automatically delete unsynced records.
- Include migration interruption and recovery tests.
- Do not install or configure MySQL.
- Drift/SQLite implementation remains a subsequent implementation task; this record does not claim that it is already wired into the application.

Q05 — PowerSync compatibility and cost spike
- PARTIAL CLIENT-SIDE SPIKE DONE 2026-09-15, real findings (not a guess — checked current docs/pub.dev, not stale training data):
  - `powersync` 2.4.0 and `drift_sqlite_async` 0.3.1 (the official, currently-Beta Drift bridge) resolve and compile cleanly alongside our existing drift 2.35.0/drift_flutter 0.3.1 stack on this Flutter 3.47.4 target — no version conflicts found.
  - Our existing `AppDatabase` (lib/data/app_database.dart) needs ZERO schema changes to adopt PowerSync — it already takes a plain Drift `QueryExecutor`. Only the connection construction would change, from `driftDatabase()` to `SqliteAsyncDriftConnection(powerSyncDatabase)`.
  - IMPORTANT for the go/no-go call: PowerSync would REPLACE `lib/application/sync_worker.dart`'s outbox, not sit beside it — PowerSync tracks local writes into its own CRUD queue, separate from our `pending_upload_intents` table. Running both would be exactly the "second competing queue" D05 forbids.
  - Real pricing checked: Free tier $0/mo (2GB sync, 2 instances) but deactivates after 1 week idle — not suited to an on-and-off evaluation. Pro tier $49/mo removes that.
  - A connector scaffold (`lib/data/powersync_connector_spike.dart`) compiles against the real `PowerSyncBackendConnector` API (fetchCredentials/uploadData) but is NOT wired into the app and has never connected to a live instance.
  - What this session could not do, and does not do on the owner's behalf: create a PowerSync Cloud account/instance, or run the Supabase-side SQL to create a `powersync_role` with replication + a password and a `CREATE PUBLICATION`. Both need the owner directly.
